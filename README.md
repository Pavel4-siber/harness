# REST API для общения с локальной моделью Ollama

Приложение на Spring Boot предоставляет REST API для диалогов с локальной моделью Ollama. Каждый диалог получает `conversationId`; передавайте его в следующих запросах, чтобы сохранить контекст. Ответ можно получить целиком или потоком, по мере генерации.

## Требования

- Java 25
- Docker Compose

## Запуск Ollama

Из корня проекта запустите контейнеры:

```powershell
docker compose up -d
```

Ollama будет доступна приложению и на хосте по адресу `http://localhost:11431`. При первом запуске Compose скачает модель `qwen3.5:4b` в отдельный Docker volume. Файлы модели и кэш не хранятся в репозитории. По умолчанию используется CPU; чтобы включить GPU, настройте поддержку GPU в Docker Compose для своей системы.

В Compose два контейнера из одного образа, а модель одна: `harness-ollama` постоянно работает как сервер, а `harness-ollama-pull` один раз скачивает модель в общий том и завершается.

Загрузка модели занимает несколько минут. Прогресс и ошибки видны в логе:

```powershell
docker logs -f harness-ollama-pull
```

Убедиться, что модель загружена, можно так:

```powershell
docker exec harness-ollama ollama list
```

Пока модель не загружена, запросы к API завершаются ошибкой `MODEL_ERROR` (HTTP 502).

Контейнерам заданы DNS-серверы `8.8.8.8` и `1.1.1.1` (см. `docker-compose.yml`): встроенный DNS Docker в некоторых окружениях не может определить адрес `registry.ollama.ai`, и модель не скачивается (`server misbehaving`). Если эти серверы недоступны в вашей сети, замените их в блоках `dns` на свои.

## Запуск приложения

В отдельном окне PowerShell выполните:

```powershell
.\mvnw.cmd spring-boot:run
```

Приложение запустится на `http://localhost:8080`. По этому адресу открывается простая страница-чат, которая использует потоковый API: ответ появляется по мере генерации, а диалог сохраняется между сообщениями.

Spring AI 2.1.0-M1 — milestone-версия, поэтому в `pom.xml` подключён репозиторий Spring Milestones (`https://repo.spring.io/milestone`).

## Настройка

Параметры можно переопределить переменными окружения:

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `OLLAMA_BASE_URL` | `http://localhost:11431` | Адрес Ollama |
| `OLLAMA_MODEL` | `qwen3.5:4b` | Имя модели |
| `OLLAMA_NUM_PREDICT` | `512` | Максимальное число токенов в ответе; при меньшем значении ответ обрывается, при большем растёт время ответа |
| `CHAT_MAX_HISTORY_TURNS` | `20` | Число последних пар вопрос–ответ в контексте диалога |
| `CHAT_MAX_CONVERSATIONS` | `1000` | Максимальное число диалогов в памяти; при превышении самые старые вытесняются |
| `CHAT_CONVERSATION_TTL_MINUTES` | `60` | Через сколько минут без обращений диалог удаляется |
| `CHAT_SYSTEM_PROMPT` | краткий промпт на английском (см. `application.properties`) | Системный промпт для каждого запроса к модели; пустое значение отключает его |
| `CHAT_TIMEZONE` | `Europe/Moscow` | Часовой пояс для текущих даты и времени, которые передаются модели |

Модель, `num-predict` и `temperature` задаются только в `application.properties` (`spring.ai.ollama.chat.options.*`); приложение передаёт их в каждый запрос явно. Для потоковых ответов в `application.properties` задан `spring.mvc.async.request-timeout=15m`: без него долгая генерация обрывалась бы по стандартному таймауту.

Пример настройки в PowerShell:

```powershell
$env:OLLAMA_BASE_URL = "http://localhost:11431"
$env:OLLAMA_MODEL = "qwen3.5:4b"
$env:OLLAMA_NUM_PREDICT = "1024"
$env:CHAT_MAX_HISTORY_TURNS = "20"
$env:CHAT_TIMEZONE = "Europe/Moscow"
.\mvnw.cmd spring-boot:run
```

Файл `application.properties` должен быть сохранён в UTF-8; если в нём появится кириллица, проверьте кодировку проекта в IDE (иначе вместо букв будут `?`).

## API диалога

Тело запроса одинаково для обоих эндпоинтов:

| Поле | Обязательное | Описание |
| --- | --- | --- |
| `message` | Да | Сообщение пользователя; не пустое, не длиннее 8000 символов |
| `conversationId` | Нет | Идентификатор предыдущего диалога, не длиннее 64 символов; если не указан, создаётся новый |

### Ответ целиком: `POST /api/chat`

```powershell
$firstReply = Invoke-RestMethod `
  -Method Post `
  -Uri "http://localhost:8080/api/chat" `
  -ContentType "application/json" `
  -Body (@{ message = "Привет! Меня зовут Анна." } | ConvertTo-Json)

$firstReply
```

Ответ содержит идентификатор диалога и сообщение модели:

```json
{
  "conversationId": "идентификатор-диалога",
  "message": "Ответ модели"
}
```

Чтобы продолжить диалог, передайте полученный `conversationId`:

```powershell
$nextReply = Invoke-RestMethod `
  -Method Post `
  -Uri "http://localhost:8080/api/chat" `
  -ContentType "application/json" `
  -Body (@{
    conversationId = $firstReply.conversationId
    message = "Как меня зовут?"
  } | ConvertTo-Json)

$nextReply
```

Ответ приходит только после полной генерации, поэтому на CPU запрос может выполняться минуту и дольше.

### Потоковый ответ: `POST /api/chat/stream`

Ответ приходит как Server-Sent Events по мере генерации. Заголовок запроса: `Accept: text/event-stream`. События:

| Событие | Данные | Когда |
| --- | --- | --- |
| `meta` | `{"conversationId": "..."}` | Первым, сразу после начала потока |
| `token` | `{"text": "..."}` | Очередная часть ответа; текст нужно склеивать по порядку |
| `done` | `{}` | Ответ завершён |
| `error` | `{"code": "MODEL_ERROR", "message": "..."}` | Ошибка после начала потока; статус HTTP к этому моменту уже отправлен (200), поэтому ошибка передаётся событием |

Полный ответ попадает в историю диалога только после успешного завершения потока. При ошибке модели или обрыве соединения клиентом частичный ответ не сохраняется.

Пример в PowerShell: тело запроса в файле (так нет проблем с экранированием кавычек и кодировкой кириллицы), токены склеиваются в сплошной текст:

```powershell
[IO.File]::WriteAllText("$PWD\body.json", '{"message":"привет, расскажи сказку"}', (New-Object Text.UTF8Encoding($false)))

[Console]::OutputEncoding = [Text.Encoding]::UTF8
$event = ''
curl.exe -sN -X POST http://localhost:8080/api/chat/stream -H "Content-Type: application/json" -H "Accept: text/event-stream" --data-binary "@body.json" | ForEach-Object {
  if ($_ -match '^event:\s*(.+)$') { $event = $Matches[1] }
  elseif ($_ -match '^data:\s*(\{.*\})$') {
    $d = $Matches[1] | ConvertFrom-Json
    if ($event -eq 'token') { Write-Host -NoNewline $d.text }
    elseif ($event -eq 'error') { Write-Host "`n[ОШИБКА] $($d.code): $($d.message)" -ForegroundColor Red }
  }
}
```

Postman показывает каждое событие отдельной строкой (новые сверху) и не склеивает токены; для удобного просмотра используйте страницу `http://localhost:8080/`.

## Ошибки

Ошибки API (кроме потока после его начала) возвращаются в общем формате:

```json
{
  "status": 503,
  "code": "MODEL_UNAVAILABLE",
  "message": "The model service is currently unavailable",
  "details": []
}
```

Некорректное тело запроса и ошибки валидации (пустое или слишком длинное сообщение, слишком длинный `conversationId`) возвращают HTTP 400. При недоступности Ollama возвращается HTTP 503 (`MODEL_UNAVAILABLE`), при ошибке модели, в том числе если модель ещё не загружена, — HTTP 502 (`MODEL_ERROR`). Внутренние ошибки возвращают HTTP 500 (`INTERNAL_ERROR`); подробности исключения остаются в логе приложения.

## Как обрабатывается запрос

Модель сама ничего не помнит: контекст диалога создаёт приложение и при каждом запросе заново отправляет модели системное сообщение, историю диалога и новое сообщение. Генерация идёт токен за токеном до естественного конца или до лимита `OLLAMA_NUM_PREDICT`.

- **История** хранится в памяти приложения отдельно для каждого `conversationId`. В контекст включаются последние 20 пар вопрос–ответ (или значение `CHAT_MAX_HISTORY_TURNS`). Число диалогов ограничено (`CHAT_MAX_CONVERSATIONS`), а диалог без обращений удаляется через `CHAT_CONVERSATION_TTL_MINUTES` минут. История сбрасывается при перезапуске и не разделяется между несколькими экземплярами приложения.
- **Системное сообщение** содержит системный промпт и текущие дату и время (у модели нет собственных часов). Оно добавляется в каждый запрос, не сохраняется в истории и не расходует лимит пар.
- **Параллельные запросы** в один диалог (включая потоковые) выполняются по очереди, чтобы история не перемешалась; запросы в разные диалоги не мешают друг другу, но Ollama на одной машине может обрабатывать их медленнее.
- **Токены и контекст.** Каждый запрос заново обрабатывает всю историю: чем она длиннее, тем дольше ответ начинает генерироваться. Лимит `OLLAMA_NUM_PREDICT` ограничивает только ответ, а не историю. Окно контекста модели ограничено; если история в него не помещается, Ollama молча отбрасывает самые старые сообщения. Размер окна можно задать свойством `spring.ai.ollama.chat.options.num-ctx`.
- **Лог токенов.** После каждого успешного ответа приложение пишет в лог строку `Chat usage: conversation=..., promptTokens=..., completionTokens=..., historyMessages=..., numPredict=...` (без текстов сообщений). `promptTokens` показывает, сколько токенов ушло на вход, `completionTokens` — на ответ. Если ответ упёрся в `numPredict`, добавляется предупреждение, что он, вероятно, оборван.
